Decision tree — "if X, use this"

The map CLAUDE.md points into. Two layers: which tool to reach for in a given situation, then — once fallow reports something — how to decide what to do about it.

Before deleting any "unused" export/file, trace it first. fallow is syntactic (oxc, no TS compiler): fully dynamic import(variable), reflection, and runtime-only consumers are invisible to it. A trace that comes back "used" means add a suppression; "not used" means it's safe. Never delete on the strength of the summary alone.

Layer 2 — what to do with a finding #

fallow's own framework (from its compliance guide). For every finding, choose exactly one:

1 · Fix it now

The finding is real and the behavior is safe to preserve by editing code.

  • delete the unused file/export
  • remove the unused dependency
  • extract / simplify a function over threshold
  • consolidate duplicated logic

2 · Encode it as an exception

The code must stay, but fallow can't infer that from syntax. Use the narrowest mechanism and say why.

  • inline suppression for one line/file
  • ignoreExports for one export
  • ignoreDependencies for one dep
  • dynamicallyLoaded / publicPackages for runtime/library surfaces
  • ignorePatterns only for generated/out-of-scope files (last resort)

3 · Change the policy

It's not one bad file — a repo-wide standard should differ. Do this deliberately, documented.

  • adjust a complexity threshold in health
  • change a rule's severity in rules
  • model a framework convention once in config

Don't raise thresholds globally just to hide a few hotspots.

Preference order for exceptions (narrow → broad): inline // fallow-ignore-next-line → ignoreExports / ignoreDependencies → dynamicallyLoaded / publicPackages / ignoreDecorators → ignorePatterns. Always document the reason. Details + the token table on Config & suppression.

Adoption loop #

  1. Run fallow (or the relevant subcommand) to see current state.
  2. Fix straightforward real issues.
  3. For each remaining finding pick Fix / Encode / Change-policy (above).
  4. Re-run after each batch.
  5. Once repo-wide state is intentional, use fallow audit as the change gate.
