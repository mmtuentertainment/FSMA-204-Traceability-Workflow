This project — FSMA 204 Workflow Product

How fallow is set up here, why the config is tuned the way it is, and what the current findings mean. Stack: Next.js 16React 19Drizzle ORM + pg OpenAPI-firstTypeScript 5.9 · Node ≥22.6. Posture: pre-production scaffold, phase 3 (provider activation) in progress.

What fallow detected (zero-config) #

Plugins: nextjstypescript drizzleopenapi-ts — all auto-detected, no config needed.

Entry points (reachability roots): Next.js routes under app/api/… + app/layout.tsx/page.tsx, drizzle.config.ts + lib/db/schema.ts, the openapi-generated types, the script-run tests, and (added by config) all tests/** test files.

The tuned config & why #

Config lives in .fallowrc.jsonc at the repo root (commented so each choice carries its reason). Summary:

SettingWhy
entry: ["tests/**/*.test.ts", "…test.mts", "…/*.mjs"]The key fix. The provider tests (tests/db/exception-review-provider-a1/a2.test.ts) aren't referenced by every npm script, so fallow saw them as unreachable — flagging the test files as unused and cascade-flagging every provider/fixture export they consume. Declaring test globs as roots makes the graph match reality. Resolved 3 false "unused files" + 6 false "unused exports".
ignorePatterns: lib/api/generated/** , lib/db/migrations/** , next-env.d.tsMachine-generated output (openapi-typescript, drizzle-kit, Next.js) — never analyze it.
duplicates.ignore: ["tests/**"]Tests legitimately repeat arrange/act/assert + fixture setup. This was the explicit ask — it dropped duplication from 6.9% (9 groups) to 2.2% (2 groups).
health.ignore: ["tests/**"]Test run() bodies are long sequential assertion lists (high cyclomatic, ~zero cognitive) — not real complexity hotspots.
rules: unused-* → warn; structural rules → errorThis is a scaffold — staged-but-unwired code is expected (per AGENTS.md). Surface unused-* as warnings; keep circular / unresolved / unlisted / duplicate-export / boundary as hard errors. Tighten unused-* back to error as the product leaves scaffold stage.

What's expected to remain during provider activation

  • 14 unused exports (warn) — fixture constants and provider functions staged ahead of being wired into a route, in lib/db/exception-review-provider.ts (e.g. reviewTraceabilityExceptionWithProvider, reserveIdempotencyRecord, appendExceptionReviewAuditEvent), plus lib/api/{exception-review,mock-recall,problem,route-boundary}.ts and lib/security/{idempotency-audit,request-context}.ts. As each gets wired into a handler, its warning disappears on its own. Trace before deleting any of them — they're consumed by tests today.
  • 2 duplication groups — lib/api/exception-review.ts ↔ lib/db/exception-review-provider.ts: the provider mirrors the fixture-repo logic during migration. Expected to converge; suppress with // fallow-ignore-file code-duplication only if it's intentionally permanent.
  • 5 complexity findings — the provider's idempotency/tenant logic + the route PATCH handler. Genuine production complexity worth tracking; not noise.

How to run it here #

# full sweep (combined)
npx fallow --format json --quiet 2>/dev/null || true

# gate your current change before committing
npx fallow audit --format json --quiet --explain 2>/dev/null || true

# why is an export flagged? (consumed by tests today)
npx fallow dead-code --trace lib/db/exception-review-provider.ts:reserveIdempotencyRecord \
  --format json --quiet 2>/dev/null || true

Setup notes #

  • Installed as a dev dependency (fallow ^2.87.0) — brings the CLI, LSP, MCP server, a version-matched Claude Code Agent Skill (node_modules/fallow/skills/fallow/), and the typed contract (fallow/types).
  • MCP server wired project-scoped in repo-root .mcp.json (does not affect other projects). See MCP tools.
  • .fallow/ (local cache / impact / snapshots) is gitignored.
  • This whole setup is documented as a batch in ops/deltas/0053-fallow-setup.md, per the repo's batch discipline.
